# Session Controller

English | [中文](README.zh.md)

Desktop analytics follows the [product collection policy](../../client/product-analytics/README.md), including its launch-time switch. Web usage is excluded.

## Summary

`@deepseek-ai/dsh-api-session-controller` owns the Host `ctx.sessionController` service and the generated Client `session`, `skills`, and `fileReferences` Remote namespaces. It serves Session lifecycle and history, the Host-generation model catalog, human background-job kill, workspace-path opening, user-invocable skill discovery, and Agent-scoped file references. Use it through API Gateway when a Client needs operations addressed by a Session.

## Use this package

The controller reads a Session's recorded preset through the optional `agentPresets.presetForSession(session)` service method. A null result means no preset was recorded; an absent service means preset identity is unavailable to the controller.

History pages and follow opening snapshots carry one `{ type: 'event', event: SessionWireEvent }` record per durable Session event. The Client retains each accepted record as one durable `SessionEventLikeEntry`; Assistant token boundaries remain inside the compact stream on `assistant/message` or `assistant/attempt`. Tool arguments, result content, failures, and `tool/result.data.meta` pass through unchanged; the controller does not resolve a Tool definition, run a presenter, or attach UI data.

Each `turn/end` record that `events`, `page`, or `follow` serves also carries `turnUsage`, outside its unchanged durable event. The [token-meter fold](../../llm/token-meter/README.md#turn-accounting) computes the complete turn's tokens, recorded cost, and unpriced-call count through that end, including retry attempts. The result is independent of step detail and whether the turn start is outside the page; invalid or incomplete accounting is `null`, not a partial total. Page and exact-interval reads use only the requested source prefix and attach summaries only to served end records. Follow seeds the same fold from its opening observation, then advances it once per accepted live event. A pure `observeEvent` subscription reads no prefix and omits the field. These summaries require neither hidden-step fetches nor a session-wide map on the wire.

`events`, `page`, and `follow` take `stepDetail`. Under `collapsed`, a step that is neither its turn's highest step, the step carrying its closing assistant text, nor the last assistant or text-carrying step before a human `user/message` steered into the turn keeps its `step/start` and `step/end` records plus a `StepDigest`; injected context retains nothing ([steered replies](../../../.agents/notes/implemented/bug-fix/2026-10-02-steered-reply-collapse.md)). Retention is decided over the whole log through the requested cut. Nested PTC records inherit their root call's step. Each retained record's `covers` states the inclusive seq range it represents, keeping the page's coverage contiguous; a page that collapsing would leave empty is served whole ([decision](../../../.agents/notes/implemented/architecture/2026-09-01-collapsed-step-digest-paging.md)).

A digest accounts for the whole step: model calls, root and nested settled tool calls, distinct recorded `filePaths`, line volume, wall time, and billed tokens. Its `elided` count alone describes the events withheld from that page. File figures use the shared `appliedFileDiffs` reading of the recorded call head, outcome, and metadata; a successful write without usable hunks retains the whole-file argument fallback. Repeated page fragments keep one step account and combine only their omitted-event counts.

`expandSteps` reads one turn's withheld events at or after the client's window head. `events` or `page` with `fromSeq` instead reads the exact inclusive interval through the cut at full detail, without activating an Agent. This interval mode rejects `beforeSeq`, a message budget, a turn window, or collapsed detail rather than silently truncating the requested data.

The Client journal validates current Session event envelopes before publishing follow snapshots, live entries, or history pages. It reuses the browser-safe Session validators for required surface markers, exact replacement endpoints, earlier unique source seqs, embedded Assistant provider metadata, request-header omissions, and tool-error consistency. Invalid records fail without field stripping or normalization; range membership and source existence remain durable-log checks on the Host.

A browser may keep a verified local copy of ordinary Session logs and install it with `ClientSessions.registerHistorySource`; only one registration may exist — one guarded slot (`sessions/history-source-slot.ts`) shared with the test-support runtime, so a second install fails identically in either — and Sessions retained afterwards consult it while subagent-addressed Sessions never do. A Session with a registered copy opens its newest window from the copy at once and follows from there, requesting stored lines: the window is published `unconfirmed` until the first remote follow opening lands, a resumed opening appends its events without replacing the window, and a snapshot that replaces it reports the divergence so the copy can repair. Older pages, step expansions, and full-history interval reads consult the copy first and fall back to the Host for any read it does not cover or that fails; each history stream logs its first failed copy read.

Local records may carry a recorded stream cut to its first-token prefix, marked `stripped` until `requireFullHistory` re-reads the window's whole range at full detail and replaces the window once with the result; page loads, expansions, and interval reads also mark `headerKey` on `request/header` records, and the Session keeps one header object per distinct content, so a window holds each distinct header once.

Each endpoint states its activation policy. List reads only stored headers and projection-cache rows: it never calls per-session stat or opens a cold Session body. A current-format cache identity may supply every list hint; a lifecycle-matching predecessor cache may supply only its version-compatible title as a stale display fact, never as an authoritative fold seed. Search, history pages, log following, skill discovery, and workspace-path opening can inspect persistence without activating an Agent; `canOpenWorkspacePath()` reports native-opening availability without addressing a Session. Cancellation requires live state; queue mutation, model, rename, prompt, and file-reference operations may resolve or resume an ordinary Session. Prompt rejects content with neither non-whitespace text nor an attachment before resolving the Agent or appending Session events; queue edits accept only non-empty text content. Prompt admission consumes opaque receipts from the injected [`fileUploads`](../../client/file-upload/README.md) Host service and resolves every same-Agent receipt before sending the complete ordered content list through `ctx.attachments`. A receipt names a staged file or a staged image, and an image receipt subjects the prompt to the same image-input check as an encoded image. Prompt retries whose `requestId` is already queued or logged return the original acceptance without inserting another message. Create and fork are the only operations that create a new Agent directly. The service applies one preset-aware resume policy and subagent ownership fence to its own methods and to the Typert Agent and Session lookups used by other Remote namespaces. Queue mutation has one narrow exception: a live child whose current projected identity is continuable and comes from its own non-seed suffix accepts the ordinary Edit, Remove, and QueueDock Steer actions across both inbox destinations. One-shot, missing, unknown, corrupt, seed-only, or cold children remain rejected without resume. The skill catalog uses a live Agent's effective working directory and scoped registry when present. Cold listing uses the projected current directory, falling back to the recorded origin and then the configured directory default. It retains the preset standing scope without activating an Agent. The authenticated delivery routes use `workspaceDesktop()` for the serving Host name and file-manager behavior. `openWorkspacePath({ path, action: "reveal" })` delegates file-manager navigation to the native adapter; omitting `action` opens the file-type association, including HTML and SVG. Both operations require the composed filesystem to map the requested Host path to the same canonical process path; unmapped remote paths are refused before a native command runs. `session.projections` normally reads an exact baseline, including current-format cold logs, and returns `kind: sequenced`. Only a read requiring migration returns `kind: migration-required` hints without `asOfSeq`; missing keys remain absent. It returns null for a missing Session. Fork callers may set `allowMigration: false` to receive `session/migration-required` instead of starting source migration; omission retains automatic migration. The Client exposes shared values and explicit-read state through `projectionsBySession`; domains select their own keys. Session-list summaries carry `agentAvailable`, updated through existing summary and status events independently of durable projections. Sequenced reads and live projection frames use the same sequence ordering; cached reads fill hints without replacing sequenced values.

Every Remote endpoint is access-controlled: a Peer whose principal is not the owner reaches an endpoint only when, on every resource the call touches, a binding of that principal kind's policy in [`dsh-api-remote-access`](../remote-access/README.md) grants a role listing the action ([Peer principals Agent Note](../../../.agents/notes/implemented/architecture/2026-10-12-peer-principal-and-remote-access.md)). The controller injects `remoteAccess` and registers a default resolver for the `session` resource kind through `typert.resources`. It reads a named `sessionId` parameter, otherwise the first object argument's `sessionId` or `address`; unrelated string parameters name no Session. An object containing both `sessionId` and `address` is invalid, even when they name the same Session. `session/events`, the deprecated `session/page`, `session/expandSteps`, `session/observeEvent`, and `session/follow` use this resolver to read `address.sessionId` for an ordinary Session address and `address.childSessionId` for a subagent address; whether access to the parent Session covers its children is the policy's rule. `session/projections`, `session/observeProjections`, `session/state`, `session/observeState`, and `session/wait` read the Session resource from `request.sessionId`, so each call and subscription names only the Sessions it may read. `session/list`, `session/search`, and `session/control` read no resource, so their calls touch the `global` resource and need a `global` role; for a non-owner caller, `session/list` returns only the rows, `session/search` only the hits, and `session/control` only the baseline projections, the retained Session identities, and projection frames, whose Session `ctx.remoteAccess.allows()` admits for the same action, so that action also belongs to a `session` role; owner results are unfiltered. `session/prompt` builds the durable `user-rpc` message source in its Remote method and records `principal` only for a non-owner caller, read through `principalOf(this.ctx.invocation)`; a source without `principal` belongs to the owner.

`events` reads one chronological page from a durable cut and returns its records, `hasMore`, and an inclusive `cursor`; omitting `throughSeq` selects the observed log end, and the compatible `page` method carries the same read with a deprecated entry point. `events`, `expandSteps`, `observeEvent`, and `follow` take an Address; projection and state operations take a Session ID. Page reads, step expansions, and Follow openings validate the supplied Address. Pure `observeEvent` and `observeProjections` subscriptions neither acquire an Observation nor establish existence: their `ready` frame carries no snapshot cursor.

List rows carry `formatStatus` when available, so Clients can identify migration-required Sessions without requesting their projections.

The `latestTurn` projection is `open` from a `turn/start` until its `turn/end`, then that end's reason kind, plus the cancellation cause for `aborted`; it is null before the first turn. A cold list row reports a cached `open` turn as `interrupted`, the closer that cold reads and the next resume append, so Clients can find Sessions whose last turn was cut off without loading their logs.

Host list generation yields between complete rows only when its configured work slice is exhausted; cheap remaining work returns without a forced yield. Request cancellation is checked per row and after each yield and rejects without partial results. Each row is synchronous; the list does not promise one cross-Session snapshot. A Session already queued as cold remains a cached row if it attaches during a yield: Client in-flight mutation replay corrects its availability, and sequenced projections supersede cached hints.

`sessions.setStepDetail` changes the reading preference without discarding loaded events. A consumer's `requireFullHistory()` takes precedence for that Session object's lifetime and recovers the loaded interval through an exact range read. Recovery preserves the live assistant prefix and existing pages, rejects stale window responses, and reports `loadingStepDetail` and `stepDetailError`; callers can retry failed reads. This policy is owned by the [full-history reader decision](../../../.agents/notes/implemented/bug-fix/2026-09-10-consumer-required-full-history.md).

Client list rows and resident Sessions use the current `sessionListMetadata` projection to reject stale blank-session hints; recency is the later of the summary timestamp and the projected last user prompt. When SessionManager creates an instance before its list row arrives, it reconciles blankness with metadata already retained for that Session. An opened conversation is therefore not reused by New Session even when an older list response still marks it blank.

`session.create` returns a Session for a new conversation, and its response names the Session actually used. A named `sessionId` is reused while it is blank (no turn has started), belongs to the requested directory, is an unarchived member of the requested Workspace, and is not written by another owner; a live Session is reused in place, and a persisted one is resumed while retaining its writer lock. The reused Session runs the requested `agentPreset`, or the configured default when the request names none: its recorded preset is not resolved, and a change is logged as `agent-preset/selected` before the Agent is published. A named Session that has started, fails the Workspace placement, or is written by another owner stays unchanged, and a new Session is created instead. A `sessionId` with no stored Session becomes the new Session's identity. A named Session in another directory fails with `session/conflict`, and one owned by subagent routing with `session/agent-busy`; both checks precede preset resolution. Creations naming one identity run in arrival order, including their preset resolution, and each response reports the preset its own request left the Session running. `session.list` includes persisted blanks using cached metadata, without opening cold log bodies.

Client list refreshes retain unchanged row objects and reuse the items array when order and values match. Each row's `retainedBy` contains positive local reference-source counts; Host metadata refreshes cannot overwrite them. Cache membership checks use a per-refresh ID set, so reconciliation grows linearly with the current list and retained cache sizes. Host summary updates replace running and Agent availability; local create/fork responses only fill missing metadata on existing rows. Removed ordinary Sessions retain projection stores only when their catalogs contain children.

Background-job rows and observation streams belong to [`dsh-api-job-controller`](../job-controller/README.md); the control stream carries projections only.

Projection reads retain loading and failure state independently of their values. Reconnect abandons reads from the previous connection, refreshes the list and parent projections, and keeps the values the new control baseline retains; live membership updates arrive through the control stream. Parent availability comes from Host summaries and remains unknown until a summary or a successful list baseline establishes it. Address lookup resolves projected children without selecting them or creating scopes.

Accepted prompts and observed running keep their Client display conversion across list refresh, reconnect, and Session-object replacement. The Manager retains these observations by Session id; they do not establish durable history. Drafts, projection stores, and sidebar display rules retain their existing behavior. The [blank rollback decision](../../../.agents/notes/implemented/bug-fix/2026-09-15-client-session-blank-reconciliation.md) defines retention and late-response handling.

The Client adapter exposes `SessionEventStream`, a Gateway `RemoteJournalStream` bound to one ordinary or direct-subagent address. It opens follow before the initial page, publishes only contiguous `replace`, `prepend`, `append`, `splice`, and `settle-assistant` changes, and repairs reconnect or sequence gaps through a tail page. Backwards paging has two verbs: `loadOlder()` pulls one Turn-aligned page, and `loadThrough(seq)` — the turn-jump loader — loops Turn-aligned pages until the window covers the target seq, lowering a shared target on repeated calls, stopping on a page that makes no progress, and reporting busy through the same `loadingOlder` snapshot bit. The Web adapter explicitly opts into cursorless Assistant frames: each opening carries the active attempt's `startedAfterSeq`, `nextIndex`, and compact stream, and every stream member becomes a Client-only `assistant/live-chunk` entry ordered between durable cursors. The Host captures a follower-local arrival ordinal with that baseline and suppresses buffered frames at or before the cut; a replacement Agent may restart frame revision at one. A durable `assistant/message` or `assistant/attempt` arriving after an active opening stays staged only when its seq follows `startedAfterSeq` and its Turn and Step match; the matching end type, seq, and index releases the durable entry. A successful message retains its transient rows until the owning `step/end`, so pending tool identities remain available for dispatch. Failed or interrupted settlements retire their rows immediately; earlier same-step retries remain visible. Revision, dense-index, or settlement gaps for a known attempt reopen follow, while a controller that missed the start ignores unknown-attempt frames and publishes their durable settlement normally. An abandoned end publishes a settlement delta without a durable entry so its transient rows retire immediately. A durable gap-repair page has no Assistant baseline, so its held notification reopens follow once for a paired page and baseline. A full-detail history record covers exactly its event seq; a collapsed-page record's `covers` also spans the withheld events beside it. A business, persistence, or unresolved continuity failure terminates the stream, while only physical carrier loss selects automatic resumption. `SessionControlStream` is a Gateway `RemoteSnapshotStream`; every opening names the Sessions whose projections the Client already holds at a linked cut, as `known` checkpoints of `asOfSeq` and the Session log chain link. The Host's baseline carries a full block, with the block's `link` from its Session log chain, for every live Session that is new or changed since the checkpoint, lists the unchanged ones by identity in `retained`, and omits the Sessions it no longer has live. A Session that becomes live after the baseline, such as one a follow activates, then arrives as one projection frame per key at its cut, so the stream states every value of every live Session, including the keys no later event changes. Publishing a Host generation abandons outstanding projection reads, refreshes the list and parent queries, and marks every Session's values as awaiting the new generation without clearing them; the Gateway reopens the control stream on the new socket, so a generation opens exactly one. A block in the new baseline replaces a Session's values, and a retained identity confirms them at their cut. A Session the baseline leaves out keeps its values, because a restarted Host holds nothing until something activates the Session: the first statement of the new generation replaces them, whether a live frame, a follow opening, a `session/projections` read or a list block, and a `cached` list block, viewed from the persisted checkpoint, replaces the values an earlier generation sequenced for the keys it carries. Keys the list summary omits (`summary: false`, such as `sessionStats`, `turnOutline` and `todos`) change only through a live frame, a follow opening or a projection read. Within a generation, a delayed control baseline cannot overwrite or clear newer sequenced values, whether they arrived through a live Session's list block, a history page, or a frame; a cached list block, viewed from the projection cache for a cold Session, yields to the connected Session's baseline whatever watermark it carries. The durable `inbox` projection carries both pending lists through the same cold-read and reconnect path as other projections. Client Agent contexts provide the identity used by the independent [`fileUpload`](../../client/file-upload/README.md) service; Session objects expose lifecycle, prompt, queue, and history operations rather than file transfer.

A reconnecting follow offers the window it holds as `resume`: `afterSeq`, the last seq its newest record stands for, and `link`, the Session log chain link the Host sent with that record. When the Host keeps a chain for the log, every record of `follow`, `page`, and `events` and every live event frame carries `link`, the [chain link](../../session/session-persistence/README.md#the-session-log-chain) of its event; a record standing for withheld events carries the link of the last one. The Host answers with a `resumed` opening that carries only the full-detail events after `afterSeq`, with the current header, projection baseline, and Assistant baseline, when its link at `afterSeq` equals `link` and at most `followResumeEvents` events follow. A snapshot opening that ends at the offered seq with the offered link also continues the held window. Otherwise it sends a complete `snapshot`, which replaces the window even when its cursor is behind the held one, so a window never continues a log whose stored bytes differ, such as after a crash that lost held events or a format migration. A follow that stays open across a promotion checks once, at its first live event, that the live log still has the opening's link at the opening cursor, and ends the generation otherwise, so the Client reconnects and gets a snapshot. A resumed reconnect keeps older pages, step digests, and expanded turns; it rebuilds live Assistant rows from the new baseline and adds durable settlements staged for an attempt that ended meanwhile. Every first opening uses a snapshot, and so does a reconnect whose newest record has no link ([decision](../../../.agents/notes/implemented/architecture/2026-11-03-resumable-session-follow.md)).

Setting `lines: true` on a follow request sends each record of a `resumed` opening and each live event frame as a `{ type: 'line', seq, line, link }` entry whose `line` is the event's stored JSONL line without its newline and whose `link` is the [Session log chain link](../../session/session-persistence/README.md#the-session-log-chain) of those bytes; a `turn/end` line entry carries the same whole-turn accounting as a decoded record. A record whose stored line the Host cannot check against the chain, or whose log keeps no chain, stays a decoded event record, and snapshot openings always carry decoded records. A line entry decodes to exactly the decoded event the Host would send without the flag, so the Client journal applies its existing range-expansion and validation to it; the browser's local copy sets this flag to append verified lines to its stored copy.

The Session object also carries local submission echoes: `session.beginSubmission` registers one before the caller serializes and prompts, and Session publishes it in `SessionSnapshot.pendingSubmissions` once the Host has accepted the prompt, as the `prompt` receipt or an `inbox` row carrying the request id shows, whichever arrives first. A conversation UI therefore shows the message from acceptance until its durable entry renders, and Chat and QueueDock exclude the matching Inbox row from the moment it arrives. The blank-to-engaging transition happens at the same acceptance. The echo stores ordered image previews and durable file references. Session derives its `transcript`, `queued`, or `steering` placement from the current running state and requested delivery mode, then retains that placement until the display handoff. The prompt's `requestId` is the correlation identity: the Host echoes it as the durable user source's `rpcId`, including pending messages in the `inbox` projection. Queued echoes retire one animation frame after queue acceptance; Chat echoes follow the admission rule below. Identified failures and abandonment retire unadmitted echoes immediately. Disposal preserves observed admission and fails other unsettled submissions. Acceptance fires `onAccept` once, in the same update that publishes the echo, so the sender can settle its composer together with the echo. Each retirement fires `onRetire` exactly once; an observed retirement includes the ordered durable attachment references so the sender can release or hand over the sent attachments. Echoes are Client memory only; reload and reconnect rebuild the conversation from durable events alone.


During uninterrupted following, transcript and steering echoes stay in Chat through Inbox acceptance and claim until their durable messages arrive. After a local Chat message is admitted, its identity remains until the Inbox watermark reaches its next-turn or next-step claim seq: Chat already renders the durable Node, while Chat and QueueDock exclude matching stale Inbox rows. Other queued messages remain visible. A replacement follow baseline withdraws receipt-confirmed echoes as observed, using their accepted attachment references; unconfirmed submissions remain pending. Host data then supplies the pending or admitted rows. Reconnecting between claim and admission can briefly omit that bubble; withdrawal confirms acceptance, not execution or failure.

The user-invocable `skills/list` metadata includes the winning provider’s optional instruction-file `path`. The composer can preview that file without loading every skill body or activating a cold Agent.

Fork copies the exact inclusive event prefix selected by `atSeq`, including a cut inside an open turn, into an independent Session without `parentSession`. Client placeholders likewise omit `parentSessionId`; list indentation applies only to subagent-origin rows, including when historical ordinary forks retain a parent id. Workspace attachment and optional title increments use the source selected for the operation. The child records its inherited marker before synthetic fork results and closing events. Omitting `atSeq` selects the latest completed turn and its standalone tail, stopping before the next turn or queued input; a nonexistent event is rejected. The chat action selects a completed turn.

A resume blocked by an existing write handle returns `session/writer-held` with the Session id; other resume failures retain `gateway/internal`.

`loadThrough(seq)` retains older pages privately until its shared target is covered or loading ends, then publishes the successful pages as one ordered prepend. Live events remain visible while history loads. A later page failure retains the successful prefix; replacing the history window discards buffered pages from the replaced window. Ordinary `loadOlder()` publishes one Host-selected page directly.

The Client's initial `follow`, reconnect openings that the Host answers with a snapshot, and `loadOlder()` request at least 50 append-origin `user/message` and `assistant/message` events and cross at least two `turn/start` events, including the partial Turn at the loaded window's beginning. The Host stops at the first Turn start satisfying both minima, or at 500 counted messages or history exhaustion, whichever comes first. Steering does not add a Turn boundary. Intervening events accompany the page without counting toward the message budget. The optional `turnWindow` on page and follow requests supplies these minima under `maxMessages`. Under collapsed step detail the Client raises the message minimum to 300 within the same cap, because a collapsed page carries fewer bytes per message. `loadThrough()` uses the same rules with a 200-message minimum per page; the 500-message cap does not limit the whole jump. Requests without `turnWindow` retain message-aligned paging.

Queue edits replace pending content with non-empty text only.

`session.attachment` receives `{ sessionId, attachment: ImageAttachmentRef }` and passes the complete reference to `AttachmentStore.readImage()`, without reading or traversing Session history. The Client supplies the message's reference through `session.readAttachment(ref)`. Connection authentication and Gateway permission checks still apply; `sessionId` selects the Session resource for the endpoint's permission check. After authorization, the handler does not check whether that Session exists and does not return `session/not-found` merely because it is absent. An authorized caller may read any image in the same store, including an image referenced only by another Session or by no Session. The response preserves the supplied reference after verifying its ID, media type, byte length, width, and height against the stored bytes. Optional `name` and `originalDimensions` pass through as caller-supplied display information and are not verified against the file. Missing or invalid objects return a terminal attachment failure. The Client's historical-image cache retains one result and browser URL per Session and attachment ID.

The controller composes `ArchivedSessionGate` through `ctx.plugin`: it loads once the Agent registry, Session store, and Workspace registry exist and unwinds with the controller. Its `agent/pre-step` listener rejects a step proposed for an archived Session or for a subagent descendant of one — read from the Session header's lineage fields, never a fork — so a late waking delivery ends its turn as `blocked` without a model request; unarchiving lifts the gate for the whole lineage. The work an archived Session still runs is reported and stopped by its owners through the Workspace registry's archive admission ([seam](../../workspace/workspace/README.md)): the running turn by the [Agent registry](../../core/agent/README.md), owned jobs by the [job registry seam](../../jobs/jobs/README.md), subagent descendants by the [Subagent](../../subagent/subagent/README.md) runtime, reminders by the [Schedule](../../schedule/schedule/README.md) plugin; this controller reports nothing itself.

## Client references

`sessions.retain(target, { source, signal? })` immediately acquires one exact Client generation and starts its shared initial history opening. The target is a known Session id or a durable direct-parent subagent address; the Host validates an explicit address when history opens. The returned reference supports idempotent `release()` and `Symbol.dispose`; its `ready` Promise follows the shared `Session.open()` result and resolves to the exact binding when that attempt settles, including when a Remote failure is represented by `openState: 'error'`. It rejects when `Session.open()` rejects, its waiter is cancelled, or the reference is released early. Cancelling one waiter does not cancel another owner's opening. `sessions.using(target, options, operation)` waits for that settlement, holds its reference until the callback settles, and propagates rejected readiness and callback failures.

References keep local Session data, scoped Contexts, and history streams alive, not Host Agents. Ordinary Session retention never adds a catalog row. Retained subagents with a known direct-parent address keep a fallback row and notify list readers even before the parent catalog arrives; these rows do not join Host-list membership. Fork-title assignment sends rename directly and applies the returned title projection without retaining the child or opening its history. Final release withdraws the generation before teardown; later acquisition can create a new generation with the same id. `binding(id)` and `scope(id)` only borrow an existing generation. `retainInfo(id)` observes stable read-only source counts independently of catalog membership and performs no history I/O. Consumer source keys are declaration-merge extensible; navigation and completion acknowledgement belong to UI consumers, not this Controller. See [Client Session references](../../../.agents/notes/implemented/architecture/2026-09-15-client-session-references.md) for ownership and teardown rules. An unknown-mode subagent address permits history reads with direct-parent validation. Successful descriptor restoration determines the displayed mode; failures remain local to the child, and control requests still require a confirmed continuable identity.

While a local copy history source is registered, the final release of an ordinary, opened Session disposes the generation's scope, and with it every binding-owned UI state, as any release does, but keeps the Session object in a warm pool instead of disposing it; its follow stops after a grace period (`warmFollowGraceMs` of the registering source's options, default 30 s). A later `retain` binds a new generation to that Session, so its window and history stay, `ready` resolves at once, and a suspended follow is re-established by offering the Host a resume point at the newest held record, so returning to a thread adds a resumed opening instead of a snapshot. Without a registered copy, release disposes as before.

One device-wide budget bounds the event text live Sessions hold in memory (`memoryBudgetBytes` of the registering source's options, default 100 MiB desktop, 25 MiB phone). After each window change, an idle pass totals each Session's page bytes and, above the budget, evicts one Session's oldest page at a time: warm Sessions' oldest pages first — a warm Session's last page disposes it through the manager — then referenced Sessions' oldest pages that lie wholly before their last reported viewport, each group ordered by the page's last view (a page never viewed counts as oldest, and ties go to the page that ends first). A later page never goes before the pages ahead of it; pages at or after a viewport, and everything of a referenced Session that reported none, are never evicted. A page the reader's own "Load earlier" or turn jump added stays for `readerLoadGraceMs` of the registering source's options (default 30 s), with every page between it and the viewport, so loading toward the first message is never undone; the total may exceed the budget by those pages until their protection ends and the budget runs again. Eviction trims the window forward (`hasMore` turns true; digests of removed turns drop) only while no older-history load, step expansion or full-history reload runs, and the next load reloads the trimmed pages from the local copy or the Host. Each run that evicts logs one `[local-copy] memory <held>/<budget> bytes after evicting <n> pages` debug line.

## Session media references

`SessionMediaReferences` mounts `GET|HEAD /api/file?path=<absolute path>` on the authenticated `connection.fetch` channel when `connection`, `fs`, and `attachments` are composed. It reads ordinary files through `ctx.fs`, including temporary paths outside registered workspaces and files in remote providers. Neither directory containment nor MIME categories restrict access; `mime-types` supplies the response type, with `application/octet-stream` for unknown extensions. GET reuses `readBytes` for preflight and ongoing byte limits; HEAD reads metadata only. All files use `ctx.attachments.imageLimits.maxImageBytes` (normally 50 MiB); exceeding this limit returns 413. A request whose `v` parameter differs from the file's current `ctx.fs` version, including a request without one, receives a `private, no-store` 302 to the same route with only `path` and the current `v`; the versioned response is `private, max-age=31536000, immutable`, so browsers reuse cached bytes until the file changes, and private file contents may enter the browser disk cache. Responses contain the complete file, ignore Range, and carry `nosniff`, and a sandbox CSP so directly opened HTML/SVG cannot execute with the API origin. The Client rewrite lives in `ui-chat` (`AssistantMarkdown`); audio/video responses are available, while Markdown audio/video player nodes remain separate work.

`SessionLinesRoute` mounts `GET /api/session/lines?sessionId=<id>` on the same authenticated `connection.fetch` channel as `/api/file` when `connection` and `sessionQuery` are composed, under the same access rules and with no configuration surface: its byte and checkpoint limits are protocol values. The body is one `SessionLinesHead` JSON line stating `start`, `through`, `cursor`, the chain `link` at `through`, and, from the first byte, the stored `header` and its `headerLink`, followed by each requested stored line terminated by `\n`. `have` carries up to 32 `seq:link` checkpoints, highest seq first; `start` is one past the highest checkpoint whose link equals the chain's link there, so a copy that agrees through that seq continues from the next byte, and no match serves the whole log from its header. `maxBytes` (4,096–8,388,608, default 1,048,576) bounds the served line bytes plus newlines while always serving at least one due line, so an oversized line travels alone in its own response. The first due line the chain cannot check answers `409 {"code":"session/line-unverifiable","seq":<seq>}` instead of unverified bytes; a log with no chain, kept header line, or stored-line read answers `409 {"code":"session/lines-unavailable"}`. A request observes the Session without activating an Agent and computes no projection, answers 404 for a missing Session or one without a working directory, and answers 400 for a subagent Session, which the copy does not store; responses are `text/plain; charset=utf-8`, `private, no-store`, and `nosniff`.

GUI model selection requires the exact provider/model pair in the available catalog; unavailable choices reject with `session/model-unavailable`. Prompt admission retains the saved route without a catalog availability gate, so request execution reports missing credentials or unavailable models. `initializeDefaultModel()` saves the first available account model after login when no other provider has a configured API key; credential checks use configured references independently of model availability. A provider with no available models rejects initialization with `session/provider-models-unavailable`. Availability never substitutes another model or rewrites a Session selection.

A successful `selectModel` response acknowledges the recorded Session selection without waiting for the default profile setting to save. The loop registers its projection; a change applies to the next step while a prepared step retains its captured choice. Default saves run in the background in submission order; a failure logs a warning and leaves the Session selection intact. A Session with no recorded selection or request reads the last successfully saved default through live `AgentOptions` accessors. An explicit choice is recorded even when it equals that default. Omitting reasoning effort clears the explicit effort and lets each request use the adapter default.

## Known Limitations and Deferred Work

<a id="known-limitations-and-deferred-work"></a>

- A single summary, the query provider's own enumeration, final sorting, and response serialization can exceed the list work-slice target; it is not a hard Host latency bound.
- The image byte cap does not validate decoded dimensions or pixel count.
- A failed follow resumption remains visible to the caller instead of retrying indefinitely.
- A resumed reconnect still replaces the held window when a durable settlement is staged, a transient Assistant row is held, or the opening carries a live attempt; otherwise it appends only its new events. Reopening a Session without a local copy still sends a snapshot.
- A resumed opening still carries the complete projection baseline; its `turnOutline` grows by about 200 bytes per turn.
- Offline replay no longer records `session/follow`: while the Host is unreachable, a newly opened Session renders its window from the browser's local copy and its follow, which offers a resume point, stays open without items until the Host is back; a thread without a copied window fails opening as a carrier failure until then.
- The raw browser upload is one streaming HTTP request without resumable offsets; a retry sends the file again from byte zero.
- File-reference completion uses the shared Agent lookup and can resume a cold Session; the `skills/list` catalog is the non-activating alternative for skill metadata.
- Accepted/running display memory lives only in Client memory and is lost on page reload.
- That memory is not shared between tabs: one tab can show a converted row while another still shows `New Session` for the same Session.
- A cold row reports `latestTurn` only after a Host that registers it has written a checkpoint for that Session; older Sessions untouched since then report none.
