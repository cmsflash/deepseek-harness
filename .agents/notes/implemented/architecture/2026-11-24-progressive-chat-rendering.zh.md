# Agent Note: Chat 渐进渲染

Status: implemented

[English](2026-11-24-progressive-chat-rendering.md) | 中文

## Problem

热 Session 保留历史，但不保留已渲染的 Chat 视图。如果必须在首个可用帧之前挂载全部已加载消息，读者加载的旧历史越多，切换就越慢。[浏览器本地副本](2026-11-07-browser-local-session-copy.zh.md)消除了历史传输等待，但没有消除渲染工作。

## Decision

Chat 立即挂载保存的阅读锚点和最新行，通过一个由文本流拥有的交叉观察器优先处理附近行，再在空闲批次中挂载其余适用的消息正文。只要对应语义行仍已加载，每个已挂载渲染器就会保留；单纯离开视口不会回收它。稳定的语义容器保留既有分页、导航和滚动归属关系；原始渲染器提供内容前，占位符预留估计高度。队列不写入滚动位置，也不复制 Session 数据。每次正文提交都委托 viewport 执行：补偿存续视觉锚点上方的增长，不消耗锚点下方保留的折叠空间。同一事务会重定位进行中的折叠，并保留尚未采样的读者移动；锚点下方的普通增长仍使用既有空间回收策略。

按键之间存在浏览器空闲时间，并不意味着读者已经停止键入。因此，打开视图和受信任的输入之后，后台挂载会先等待配置的安静间隔，再让出一次渲染机会。输入会重启同一个可取消等待；可见行不受等待影响。[Chat 配置](../../../../packages/client/ui-chat/README.zh.md#scroll-ownership)控制这段等待，不增加手动渲染模式。

行间距使用由 viewport 拥有的标记，精确反映提交后 DOM 的空内容与引导标记条件。React 提交期间替换占位符，会使行短暂为空；依赖后代的相邻行 CSS 因而使后续子树失效，即使最终该行仍非空。初始同步、严格筛选的 DOM 变动和批次后同步，仅在最终条件变化时更新标记。任意返回 null 的渲染器仍保留原有间距。

每批共用一次同步 React 提交。下一批大小根据浏览器可用空闲时间及上一批的提交和布局开销确定，增长最多翻倍，并至少处理一个渲染器以保证前进。每次提交后的布局读取会将延迟的样式计算纳入估计。若共享布局本身已超出空闲额度，该批仍将渲染器工作限制在此额度内，并只支付一次共享布局成本；扣除无法容纳的固定成本会使每批始终只有一行。这一例外可能超出单次空闲时段，必须检验输入延迟。批次之间让出执行权，使浏览器能处理输入与布局，而不是把全部初始卡顿推迟到另一个任务。可见行会立即离开空闲队列。最后一行离开队列时，观察器断开，待执行调度取消；已销毁队列的回调不能向其他视图挂载内容。不支持交叉观察的浏览器立即渲染；不支持空闲回调的浏览器通过一个帧和一个任务让出执行权。

保存的锚点可能位于消息深处，超出该消息的估计高度。因此，恢复滚动前必须已有真实正文：只对齐估计占位符可能使其完全落在观察缓冲区外，永远无法变为可见。精确保存的节点及分组部分在本次视图挂载期间保持立即渲染。

## Alternatives considered

持续虚拟化减少保留的渲染工作，但会使屏幕外文本无法被原生查找和无障碍浏览访问。拦截键盘快捷键无法覆盖浏览器菜单查找，或焦点已在浏览器界面中的情况。回收任意渲染器输出还会丢失组件持有的状态；外观被动的 DOM 不能证明不存在此类状态。渐进挂载保留原始渲染器，并自动恢复完整的已加载文本记录，不需要手动切换渲染模式。

把全部剩余内容放进一个延迟任务，只会转移卡顿。CSS 屏幕外布局跳过仍保留全部渲染与解析工作，不能限制初始挂载工作量。保持非活动视图挂载会改变作用域与状态的生命周期，并在读者离开后继续占用内存；本决策不需要这样做。

## Consequences

初始切换执行的复杂渲染更少，但容器创建、总工作量和完整视图的内存仍随已加载历史增长。单条异常昂贵的消息可能超出一帧预算，因为其渲染器不能被抢占。队列填充期间，原生搜索和无障碍浏览可能暂时找不到延迟挂载的文本；所有已加载消息会自动变得可用。后台工作必须测量到完成，包括最后一次停顿，不能只用首帧判断。

单元测试约束队列归属、取消、立即渲染回退、可见行优先级、渲染器状态保留和深锚点恢复。组装后的滚动测试覆盖分页、实时跟随、展开状态保留和位置恢复。渐进历史预期输出记录自动完成、可见内容稳定，以及无需键盘快捷键的原生搜索。[手动浏览器诊断](../../../../benchmarks/long-session-browser/README.zh.md)分别测量首个可用视口、填充期间的受信任键入及完整渲染完成，不新增 CI 时间阈值。既有[浏览器性能预算](../testing/2026-09-06-frontend-performance-budgets.zh.md)仍由独立记录管理。
